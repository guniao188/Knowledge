# 查找 Odoo 插件 / 模块

当用户用自然语言描述业务需求时，按本流程检索并给出可落地的模块候选，而不是空泛建议「可以开发」。

## 何时启用

- 用户说：有没有插件、现成模块、OCA、应用市场、apps、付费模块、要不要二开
- 用户描述进销存/制造/财务/外贸/审批/接口等业务点，希望先找现成方案
- 需要对比免费 vs 付费、CE vs EE 依赖、版本是否匹配

## 执行前先对齐的信息

若用户未说明，先基于上下文推断；缺关键信息时只问最少问题（一次最多 2–3 个）：

1. **Odoo 版本**：如 16.0 / 17.0 / 18.0 / 19.0（优先按用户指定；未指定则同时标注各候选支持版本）
2. **版本类型**：Community / Enterprise（影响依赖与官方应用可用性）
3. **场景关键词**：业务目标、必须有的能力、可接受的替代方案
4. **约束**（如有）：必须开源、预算上限、是否接受 OPL/专有授权、是否只要中文/中国本地化

未给出版本时：仍可检索，但结论必须标明「版本兼容性未确认」。

## 检索流程（必须实际查，不能凭记忆编造）

按顺序执行；每个来源至少做一轮针对关键词的检索，并打开 2–5 个最相关详情页核对。

### 1. 提炼检索词

从需求抽出中英双语关键词，例如：

- 业务词：approval workflow / 审批流、subcontracting / 工序委外、PLM、EDI、wechat / 企业微信
- 技术词：模块技术名猜测、依赖应用（sale、stock、mrp、account…）
- 同义词与近义模块族：不要只用一个词；换 2–3 组关键词再搜

### 2. Odoo 官方应用市场

优先检索：

- 浏览/搜索：https://apps.odoo.com/apps/modules
- 带版本过滤示例：`https://apps.odoo.com/apps/modules/<version>`（如 `19.0`）
- 关键词搜索：在应用市场搜索框使用英文业务关键词为主，中文为辅

对每个候选记录：

| 字段 | 说明 |
| --- | --- |
| 显示名 / 技术名 | Apps 页标题与 Technical Name |
| 作者 / 发布商 | 公司或 OCA |
| 支持版本 | 是否包含目标版本 |
| 价格 | Free / 具体金额+币种；是否按数据库购买 |
| 许可 | AGPL-3 / LGPL-3 / OPL-1 / Other proprietary 等 |
| 依赖 | 是否依赖 Enterprise 应用、必要社区模块 |
| 链接 | 详情页 URL |
| 匹配度 | 完全匹配 / 部分匹配 / 仅相关 |

价格必须写清楚，禁止只写「收费」：

- **免费**：标明 Free / €0
- **一次性购买**：金额 + 币种（EUR/USD）+「Apps 标价（通常按数据库）」
- **看不出计费方式**：写「Apps 标价为 X，是否含维护/多库需以商店结算页为准」
- **厂商另有订阅/实施费**：在备注标明「商店价以外可能另有服务费」
- **汇率**：不要擅自换算成人民币，除非用户要求；可附注「以 Apps 页面币种为准」

### 3. OCA（必查）

并行查两个入口，避免漏掉：

1. **OCA Apps**：https://apps.odoo-community.org/  
2. **GitHub OCA 组织**：https://github.com/OCA  
   - 用 GitHub 搜索：`org:OCA <keywords>`  
   - 或按主题仓库（如 `sale-workflow`、`purchase-workflow`、`account-financial-tools`、`stock-logistics-workflow`、`server-ux`、`web` 等）进入后按模块目录名检索
   - 核对目标版本分支是否存在（`16.0` / `17.0` / `18.0` / `19.0`…）
   - 阅读模块 README / `__manifest__.py` 的 `name`、`summary`、`depends`、`license`、`version`

OCA 模块默认视为**开源免费**（常见 AGPL-3/LGPL-3），但仍要写明：

- 许可证
- 维护活跃度信号（最近提交、是否有目标版本分支、issue 情况——简要即可）
- 部署成本：免费下载 ≠ 零实施成本；若适配/依赖较多，在「落地成本」里说明

也可交叉验证：OCA 模块常同步出现在 apps.odoo.com（作者显示 OCA）。

### 4. 必要的交叉核对

- 同一功能可能同时有 OCA 免费方案与 Apps 付费方案：两者都列，并对比
- 声称支持某版本时，以 Apps 版本标签或 GitHub 分支/manifest 为准，不以标题年份臆断
- 付费插件若依赖 Enterprise，明确写出「需 Odoo Enterprise」
- 不要推荐明显停更、仅旧版本、或描述与需求严重不符的模块，除非没有更好选项并注明风险

## 输出格式（对用户）

用简洁中文回复，结构如下：

### 需求理解

1–3 句复述要解决的问题与关键约束（版本/CE·EE）。

### 推荐结论

先给结论：

- **有较匹配的现成模块** / **仅有部分匹配** / **未找到合适现成模块（可能需二开）**

### 候选列表

按推荐顺序用表格或条目列出（通常 3–8 个）：

1. **模块名**（技术名）
2. 来源：Odoo Apps / OCA / 两者
3. 匹配说明（对应哪些需求点、缺什么）
4. 版本兼容
5. **费用**：免费或金额+币种+已知计费说明
6. 许可
7. 链接

### 费用汇总

单独一小节，把所有付费项列清：

- 模块购买费（逐个）
- 可能的隐性成本：Enterprise 订阅、实施/配置、二次开发、多数据库授权未确认项
- 若全免费：写「模块本身免费；实施与维护另计」

### 建议下一步

给 1–3 条可执行建议，例如：优先试用哪个 OCA 模块、付费模块是否值得买、哪些点仍需二开。

## 质量红线

- 必须实际检索网页/GitHub；不得凭训练记忆捏造「有某某模块、价格 XX」
- 找不到就明确说找不到，并给出最接近的替代或二开边界
- 价格以页面当前标价为准；抓取失败则写「未能读取标价」并给出链接让用户确认
- 不承诺官方支持、不替厂商做合同解释；许可与采购条款以商店/仓库原文为准
- 保持简短：用户要的是「有没有、贵不贵、适不适合」，不是长篇调研报告
